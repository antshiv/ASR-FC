# GD3000 read-only bring-up, 2026-08-25

## Test boundary

The FRDM-KV31F was flashed through its P&E OpenSDA interface with the
`gd3000_status_probe` image. The firmware held `EN` low, released `RST_B`, and
sent only the read-only GD3000 `NULL0` through `NULL3` commands.

## Result

The OpenSDA programming cycle completed and the application emitted status at
115200 baud through `/dev/ttyACM3`. Seven consecutive captures returned:

```text
NULL0..3: 0xFF 0xFF 0xFF 0xFF status0=0xFF int=0 reset=1 fault=1
```

This is not a passing GD3000 identity or status result. It indicates that MISO
remained high or floating during every transaction. It also does not identify
a GD3000 fault: this first probe incorrectly treated the byte returned during
the request as the requested register value.

## Interpretation

NXP AN5169 reads the MC33927/GD3000 as a pipelined protocol: send `NULLn`, then
send `NULL0` in a second chip-select transaction and use the second response.
The revised probe implements that exact read sequence. The lit VLS indicator
also means the earlier claim that the IC necessarily lacked power was not
established by this capture.

## NXP reference baseline

The protocol behavior is grounded in NXP's `AN5169-SOFTWARE` package for the
Kinetis KV4x quad-motor reference design, not inferred from the Antshiv probe.
In that package:

- `peripherals/mc33927.c` implements each status read as `NULLn` followed by
  `NULL0`, retaining the second response.
- `peripherals/peripherals_init.c` configures the MC33927/GD3000 only after
  establishing reset, SPI, PWM polarity, output masks, and dead-time handling.
- Its FTM setup explicitly accounts for active-low high-side inputs.

The vendor source remains an external reference rather than copied production
code. ASR-FC keeps a small portable protocol contract and will place MCU pin,
DSPI, FTM, ADC, and fault behavior behind the KV31F platform adapter.

Primary references:

- <https://www.nxp.com/design/design-center/designs/kv-series-quad-motor-control%3AKINETIS-DRONE-REFERENCE-DESIGN>
- <https://www.nxp.com/products/GD3000>
- <https://www.nxp.com/design/design-center/development-boards-and-designs/FRDM-GD3000EVB>

## Next controlled gate

1. Keep `EN` low and do not send configuration or flag-clear commands.
2. Confirm `RST_B`, `CS`, `CLK`, `MOSI`, `MISO`, `INT` and `EN` pad levels.
3. Repeat only pipelined `NULL0` through `NULL3` reads.
4. Compare reset-state evidence with SR0=`0x80`, SR1=`0x00`, SR2=`0xFF`, and
   SR3=`0x00`; do not require those values after faults or configuration.
5. Treat constant `0x00` or `0xFF` across every register as a failed
   communication gate.
6. If communication still fails, inspect CS/CLK/MOSI/MISO with the Saleae.
7. Do not proceed to PWM until status reads are credible and the active-low
   high-side input polarity and board jumpers are explicitly validated.

The revised NXP-style status image was then flashed successfully. Startup pad
evidence was:

```text
RESET-LOW  rst=0 en=0 cs=1 clk=0 mosi=0 miso=1 int=0
RESET-HIGH rst=1 en=0 cs=1 clk=0 mosi=0 miso=1 int=0
```

All four pipelined reads still returned `0xFF`. The response-pipeline defect is
therefore fixed, but communication is not yet established. MISO is high at
idle and remains high through the transaction, so the next gate is pin-routing
and electrical waveform inspection rather than changing status decoding.

The FRDM-KV31F exposes native DSPI0 on `PTE16` through `PTE19`, but the
FRDM-GD3000EVB does not route its J2 SPI signals there. NXP's board-specific
compatibility table maps the stacked shield to `PTC19` (CS), `PTC18` (MOSI),
`PTC17` (MISO), and `PTC16` (CLK). A hardware-DSPI diagnostic on the PTE pins
therefore tested the wrong physical connector and was discarded. The probe
retains the PTC mapping and uses inspectable GPIO mode-1 transfers.

A weak pull-down was then enabled on the board-specific `PTC17` MISO input.
The idle level and every clocked response changed from `0xFF` to `0x00`:

```text
RESET-LOW  rst=0 en=0 cs=1 clk=0 mosi=0 miso=0 int=0
RESET-HIGH rst=1 en=0 cs=1 clk=0 mosi=0 miso=0 int=0
NULL0..3: 0x00 0x00 0x00 0x00
```

This is not a valid all-clear status. It demonstrates that the MCU is reading
its own weak MISO bias and that the shield is not driving a response during
the transaction. Software status decoding and response pipelining cannot
resolve that electrical boundary.

No motor phase was energized during this test.
